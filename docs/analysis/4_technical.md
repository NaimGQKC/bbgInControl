# Sparrow AI: technical review (architecture, reliability, security, ops)

State: `pytest -q` = 242 passed (SQLite; the suite can run on Postgres with `TEST_DATABASE_URL`, but there is no CI at all). The guardrails are real and the code is readable. The weak points are the cracks between process boundaries (crash, retry, concurrency, Postgres limits) and having no eyes on production.

## Architecture verdict
Monolith + Postgres queue + in-process worker is right for 5-500 agents; `FOR UPDATE SKIP LOCKED` is used (jobs.py:87), so several instances are safe at claim time. Do not add Redis/Celery. What does not fit: one worker thread inside the web process (one slow LLM turn, up to 25s x 2 attempts x 6 steps, delays every first message; the 30s promise breaks at roughly 50+ active agents or a prospecting burst) and safety state living in JSON blobs. Run `worker.py` as its own Railway service with 2-4 threads from ~30 agents.

## Findings

### HIGH
1. **A transient LLM error permanently kills the AI for a lead.** `run_ai_turn` swallows every exception and calls `do_handoff` (engine.py:1086-1092), which sets `human_owned=True`; only the agent texting "Sigue con X" resumes it. The job never retries. A 30s Azure 429/5xx hands every active chat to humans and floods agents. Fix: re-raise timeouts/429/5xx so the job retries with backoff (2 tries); hand off only on 4xx/content-filter; cap alerts per account per hour.
2. **Duplicate or lost sends.** (a) `httpx.TimeoutException/ConnectError` are not `WhatsAppError` (whatsapp.py:50, engine.py:122): a read-timeout after Meta accepted the message stores nothing and the job re-sends 30s later, so the owner gets the first message twice. (b) The Message row is committed only after the POST (engine.py:121) and `job_first_contact` sets `status="contacted"` after that; any exception or kill in between re-runs the job and re-sends. (c) If Meta echoes API sends, the echo can arrive before our commit and `handle_echo` marks the lead `human_owned` (engine.py:600). Fix: outbox: insert `Message(status="sending")` and the lead status in one commit BEFORE the POST; catch `httpx.HTTPError`; never auto-retry a template after an ambiguous failure; make `first_contact` check "already sent" from `messages`.
3. **Errored webhook events are lost forever.** `process_event` stores `ev.error`, and `sweep_unprocessed` only retries `error == ""` (webhooks.py:124-134). Real trigger: two near-simultaneous first messages from one owner both INSERT the `ai_turn` job (jobs.py:48 is select-then-insert); the loser hits the unique `dedupe_key`, and the whole event, owner message included, rolls back. Postgres length overflows do the same (finding 7). Fix: retry errored events 3x then alert the operator; `INSERT ... ON CONFLICT DO NOTHING` in `schedule`; `with_for_update` on the lead in `handle_inbound`.
4. **Nobody is told when production breaks.** `/health` returns ok without touching DB or worker (web.py:632). Failed jobs, errored webhook events, silent AI caps and `send_failed` live only on `/admin` or in logs. `alert_ops` (WhatsApp to the operator) already exists. Fix in a day: external uptime check on a `/health` that runs `SELECT 1` and checks the oldest due job age; a `watchdog` job every 5 min that alerts when failed jobs > 0, a due job is >3 min late, unprocessed webhook events exist, or LLM errors >3/hour; Sentry free tier.
5. **No migration path.** `create_all` (db.py:56) never alters tables and every instance runs it at boot, concurrently during Railway's overlapping deploys. Adopt Alembic now: baseline the current models, `alembic stamp head` on prod, `alembic upgrade head` as pre-deploy command. "JSON only" is already debt: consent proof (`ack_at`), prospecting pause state, rate counters and language sit in `account.settings`.
6. **Secrets fall back silently.** Encryption derives its key from `SESSION_SECRET` (default `change-me-too`) when ENCRYPTION_KEY is unset (crypto.py:10-16); no startup check. Rotating SESSION_SECRET would make every stored Meta/Google token undecryptable. Single Fernet, no rotation. `META_VERIFY_TOKEN` defaults to `sparrow-verify`. Fix: refuse to boot in live mode without ENCRYPTION_KEY, SESSION_SECRET, ADMIN_PASSWORD, META_APP_SECRET; use `MultiFernet`; keep the key in a password manager (a DB backup is useless without it).
7. **Postgres column limits are unverified; SQLite hides failures.** Free text goes into `String(N)` unclipped: the model's `address` into `lead.address` (300) and `Meeting.address` (engine.py:900-915); intake `name/zone` (200), `listing_url` (500), `source` (40) (engine.py:200-215, web.py:586). On Postgres the commit raises AFTER the Google event exists: orphan event, poisoned session, retry creates a second event (`request_id` is stored, never looked up). One bad item also 500s a whole intake batch. Fix: clip at the boundary, free-text columns to `Text`, per-item try/except, look up `sparrow_request_id` before `create_event`, run the suite on Postgres in CI.

### MED
8. **Public cost abuse.** `POST /start` makes unlimited accounts with no captcha/IP limit; each token gets 40 `help_chat` calls (vision, 4 MB images) on your Azure budget, `/help` WhatsApps you on every call, `/places` costs CASAFARI lookups (web.py:93, 434, 546). Request bodies are unbounded. Fix: Turnstile on `/start`, per-IP limit, global daily help-chat counter, body size cap.
9. **Intake and onboarding tokens are weak bearer secrets.** `/intake/{key}` (web.py:586) has the key in the path (so in access logs), no rotation, no per-account cap for warm leads. A leaked key means mass first messages from the agent's own number and a quality downgrade. `/o/{token}` is the only credential for a live account (alert phone, `extra_context` that enters the system prompt, prospecting config), also logged and sent in Referer to connect.facebook.net. Fix: `Referrer-Policy: no-referrer`, `Authorization`-header intake key with rotation, warm daily cap (~30) and max items per request, expire onboarding tokens once live.
10. **Admin: Basic auth, no CSRF, no lockout.** Browsers attach Basic credentials cross-site, so a page you visit can POST `/admin/accounts/{id}/send` (arbitrary text from an agent's number to any non-lead; this path bypasses `can_contact` by design, admin.py:134-155) or `go_live`/`pause`. Add an Origin check or CSRF token, failure lockout, Cloudflare Access/Tailscale. `/docs` is public.
11. **Opt-out hash is reversible; opt-out is per agent.** `sha256("sparrow-suppress:"+phone)` (prospecting.py:200) over ~10^9 numbers is brute-forceable in seconds: use `HMAC(pepper, phone)`. All `phone_suppressed` events are loaded into Python on every pull (prospecting.py:257): use an indexed table. A BAJA to agent A does not stop agent B's intake from messaging the same owner; I would make BAJA Sparrow-wide.
12. **Settings JSON read-modify-write loses updates.** `acc.settings = {**acc.settings, ...}` (web save `new = {**old,...}`, auto-pause, counters, operator) overwrites the whole blob. A safety pause can be erased by a concurrent agent save, breaking "never auto-resumes". Fix: `with_for_update()` on the account row for settings writes, or a separate table for pause/ack. I grepped every `facts/settings/external/tags/offered_slots/payload` write: all reassign, none mutate in place, so tracking is correct today but fragile (`MutableDict` or a lint test).
13. **Meta connect trusts browser-supplied ids.** `waba_id` and `phone_number_id` come from the client; the check `get_phone_number` swallows its error (onboarding.py:276). Inbound routing takes the first Integration whose JSON `phone_number_id` matches (webhooks.py:148-151, no unique index, no order), so an account claiming another's id can swallow that agent's inbound. Fix: require the id in `list_phone_numbers(waba_id, token)`, add a unique index, real columns.
14. **AI account cap ghosts owners.** `account_budget` returns silently (engine.py:1049): no handoff, no alert. Always hand off and alert; warn the operator at 80%.
15. **Batch claim can double-run jobs.** `_claim(limit=5)` marks 5 jobs running at once; the 5th can wait >10 min behind slow LLM turns and be re-queued by another instance (`STUCK_AFTER`, jobs.py:74-84) while still in the first worker's list. Claim one at a time, heartbeat `claimed_at`, cap attempts on the stuck path.
16. **Retention vs privacy promise.** `webhook_events.payload` (raw bodies with phones), `llm_turns`, `messages`, `events` (even `lead_rejected.raw` phone) are never purged, and the sweep scans `webhook_events` every 2s with no index on `processed_at/received_at`. Add a nightly retention job (webhook payloads 14 days, done jobs 30 days) and the 12-month agent deletion the policy promises.
17. **AI turns are not reproducible.** `llm_turns.transcript` holds outputs and tool I/O only, not the system prompt, history, prompt version or token usage (engine.py:1074). Store a prompt version (git sha) + prompt hash + usage. The only eval is the manual `scripts/ai_rehearsal.py`.

### LOW
18. Unpinned `requirements.txt` (`>=`, pytest and anthropic in prod), no lockfile, no `.dockerignore` (local builds bake `.env`/`*.db`), root user. Pin with uv/pip-compile.
19. Prompt injection blast radius is contained (model sees one lead, narrow tools, `book_slot` only accepts offered slots, `_` keys code-only). Residual: `save_facts` takes arbitrary keys and unbounded values that persist into later prompts and calendar text (engine.py:1066); `meeting_type` is not validated; replies are unfiltered (links, prices, "I am a person"). Add key allowlist, 500-char clip, an output check, and an injection set in the rehearsal script.
20. Google OAuth `state` never expires and has no nonce (`URLSafeSerializer`, web.py:29): use timed serializer + cookie nonce. `calendar.events` reads all events; use `calendar.events.owned` if sufficient.
21. Time handling is sound (naive UTC, `zoneinfo`, 09-21 clamp) but has no DST test. `_booking_locks` is per process: two instances can double-book (use `pg_advisory_xact_lock(account_id)`).
22. Signatures are correct (Meta HMAC with `compare_digest`; Stripe with 5 min tolerance). The no-secret bypass is gated on `whatsapp_mode == fake`, so a mis-set mode in prod disables both: fail boot. GET verify uses `==`.
23. Anthropic backend has no timeout or retry config and fixed `max_tokens=800` (llm.py:83). Add a per-turn wall-clock budget (~45s).
24. Backups and runbook absent from the repo: confirm Railway backups, weekly `pg_dump` off-platform, one restore drill, a one-page runbook, and a global `SENDING_ENABLED` kill switch.

## Guard chain audit
Every lead-facing send goes through `send_to_lead`: the only direct client calls are engine.py:116/119 (leads), :140 (Sparrow-number alerts, templates), :704 (agent command reply) and admin manual send (admin.py:147/150, blocks numbers that are leads only). `can_contact` runs after `s.refresh(lead)`, so G8 and opt-out races are tight; the 24h window is correct; template vs text is chosen by callers (reminder does it properly). Gaps: opt-out per account (11); callers ignore `send_to_lead`'s False (`lead.introduced=True` even if blocked, engine.py:1146); echoes untested live and racy (2c).

## Tests: covered vs missing
Strong on G1-G14, flows, prompts, i18n, prospecting, signatures, stuck-job recovery, all on fakes with a frozen clock. Missing top 10: (1) concurrent job/inbound processing on Postgres; (2) kill after POST and `ReadTimeout` on send, exactly one message; (3) whole suite on Postgres in CI with length overflows; (4) LLM 429/timeout does not hand off permanently; (5) errored webhook event retried and alerted; (6) injection corpus asserting tool/state outcomes; (7) DST weeks (29 Mar, 25 Oct) for slots/reminders; (8) admin CSRF and `/start`/`/help`/`/intake` limits and size caps; (9) Alembic upgrade on seeded Postgres; (10) live mode refuses default secrets at boot.
